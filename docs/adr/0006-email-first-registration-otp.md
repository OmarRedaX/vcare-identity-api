# ADR 0006 — Email-first registration with a 6-digit code; verify-email flow removed

- **Status:** Accepted • **Date:** 2026-09-15 • **Deciders:** identity-team

## Context
`POST /api/auth/register` returned `409 Conflict` for a known email, revealing whether someone holds a vcare
account — health-adjacent personal data — while forgot-password and resend-verification deliberately hide it.
Accounts were also created unverified, requiring a separate verify-email / resend flow and table, with Care
gating booking on `ev`. PRD goal: a patient books within 3 minutes of landing.

## Decision
- **Step 1 — `POST /api/auth/register/start` `{ email }`** always returns `202`. Unknown email: create a
  `registration_challenges` row (invalidating earlier open challenges for that email) and an outbox job
  `send_registration_code`. Known live email: create no challenge, enqueue `send_account_exists_notice` for that
  user. Rate limits: 3/h per email (hashed key), 5/h per IP.
- **Step 2 — `POST /api/auth/register/complete`** `{ email, code, password, fullName, role, timezone, locale, phone? }`,
  `Idempotency-Key` required. In one transaction: load the latest open challenge, compare
  `HMAC-SHA256(OTP_PEPPER, code)` in constant time, increment `attempts`, and on success set `consumed_at` and
  insert the user with `email_verified_at = now()` and role-dependent status (patient `active`, doctor
  `pending`). Wrong, expired, consumed, or 5th-failure (which invalidates the challenge) → `400 ValidationFailed`
  (`field: code`). `409 Conflict` only on a concurrent-registration race after ownership is proven. Rate limit
  10/h per IP.
- **Code:** 6 digits from a CSPRNG, **generated by the worker at send time** (ADR 0007), stored only as the HMAC
  hex; `expires_at` = send time + 10 min; max 5 attempts. `OTP_PEPPER` is a secret; rotating it invalidates
  outstanding codes (≤ 10 min of impact).
- **Removed:** `POST /api/auth/verify-email`, `POST /api/auth/resend-verification`, table `email_verifications`.
  Calling `register/start` again is the resend.
- **`ev` claim kept** and always `true` for accounts created this way, so Care's `EmailNotVerified` check needs no
  change.

## Consequences
- ➕ No account enumeration on any public auth route; every account's email is proven before it exists.
- ➕ Fewer endpoints and tables than before; one email flow instead of two.
- ➕ Code works across devices (read on phone, type on laptop), fitting the 3-minute goal.
- ➖ A 6-digit code is only safe with the attempt cap, short TTL, per-email/IP limits, and the pepper.
- ➖ Registration depends on email delivery latency (mitigated by outbox lag alerting, ADR 0007).
- ➖ Contract change: `/register` replaced; verify/resend removed; hub PRD §14 appendix must be updated.

## Alternatives considered
- **Uniform `202` single-step register + "account exists" email** — no leak, rejected by the user in favour of
  proving ownership before account creation.
- **Keep `409`** — simplest UX, rejected: leaks health-adjacent account existence.
- **Magic link instead of a code** — no brute-force surface, rejected: continues on the device that opened the
  email and link scanners can consume single-use links.
- **Code, but keep verify-email/resend** — rejected: two flows for cases that are out of scope (email change) or
  handled by ops (admins).
