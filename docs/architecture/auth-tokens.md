# User Tokens and Sessions

How Identity proves who a user is to itself, to Care, and to future services — without any of them
calling Identity per request. Decision record: [ADR 0002](../adr/0002-asymmetric-jwt-rotating-refresh.md).
Service tokens are covered in [service-auth.md](./service-auth.md).

## 1. Signing keys (EdDSA / Ed25519)

- Every token Identity issues (user and service) is a JWS signed with **Ed25519** (`alg=EdDSA`) via `jose`.
  The protected header carries `kid`.
- Private keys come only from the `JWT_PRIVATE_KEYS` secret: a JSON array of
  `{ "kid": "identity-2026-09", "privateJwk": { "kty": "OKP", "crv": "Ed25519", "d": "…", "x": "…" } }`.
  `JWT_ACTIVE_KID` names the key used for signing. Keys never live in the repo, logs, or the database.
- `GET /.well-known/jwks.json` publishes the **public** half of every key in `JWT_PRIVATE_KEYS`
  (current and previous) with `Cache-Control: public, max-age=300`. The set is built once at boot and
  served from memory (budget p95 < 10 ms).
- Consumers (Care, Identity's own guards) cache the JWKS and select the key by `kid`. On an unknown `kid`
  they refetch the JWKS at most once per minute before rejecting.

### Key rotation procedure
Timeline constraints: access TTL = 15 min, JWKS cache = 5 min, refresh TTL = 30 days (refresh tokens are
opaque and not signed, so only JWTs depend on keys; service tokens live 300 s).

| Step | Action | Wait before next step | Why |
|---|---|---|---|
| 1 | Generate a new Ed25519 keypair with a new `kid`; **append** it to `JWT_PRIVATE_KEYS`; keep `JWT_ACTIVE_KID` on the old key; deploy | ≥ 1 access-TTL (15 min) and ≥ JWKS cache (5 min) | every consumer's cached JWKS now contains the new public key |
| 2 | Set `JWT_ACTIVE_KID` to the new `kid`; deploy | ≥ refresh-TTL (30 days) — per CLAUDE.md; the hard minimum for JWTs is one access-TTL | new tokens are signed with the new key; tokens signed with the old key still verify |
| 3 | Remove the old key from `JWT_PRIVATE_KEYS`; deploy | — | old key no longer published or usable |

**Emergency rotation (key compromise):** do steps 1 and 2 in one deploy, immediately remove the
compromised key (step 3), and revoke all refresh-token families platform-wide. All sessions must log in
again; outstanding access tokens signed with the compromised key fail verification once consumers
refetch the JWKS (≤ 5 min). Runbook: [runbook.md](../runbook.md) → Rotate the signing key.

## 2. User access token (15 minutes)

| Claim | Value |
|---|---|
| `iss` | `vcare-identity` |
| `aud` | `["vcare-identity", "vcare-care"]` |
| `sub` | user id as a string (e.g. `"1042"`) |
| `typ` | `user` |
| `role` | `patient` \| `doctor` \| `admin` |
| `status` | `pending` \| `active` \| `rejected` (never issued for `suspended`; `rejected` accounts can sign in — ADR 0004) |
| `ev` | boolean — email verified at issue time; always `true` for accounts created by `register/complete` (ADR 0006) |
| `iat`, `exp` | `exp = iat + ACCESS_TOKEN_TTL_SECONDS` (900) |
| `jti` | random UUID, for log correlation |

- Transport: `Authorization: Bearer <token>` only. Never in a cookie, never in a URL, never logged.
- `user-guard` verifies signature (by `kid`), `iss`, `aud` contains `vcare-identity`, `typ=user`, `exp`
  (clock skew tolerance 30 s). Expired → `401 TokenExpired`; anything else invalid → `401 Unauthorized`.
- Claims are a **snapshot**: `role`, `status`, `ev` change only when a new token is issued (next login or
  refresh). Care relies on `ev` for "patients must have a verified email before booking".

## 3. Refresh token (30 days, rotating)

- Opaque 256-bit random value (base64url), generated by `pkg/utils/crypto.ts`. Only `sha256(token)` is stored
  (`refresh_tokens.token_hash`).
- Delivered only as `Set-Cookie: vcare_rt=<token>; HttpOnly; Secure; SameSite=Strict; Path=/api/auth; Max-Age=2592000`.
  The path covers `/api/auth/refresh`, `/api/auth/logout`, and `/api/auth/change-password`; the browser never
  sends it anywhere else. It is never in a response body.
- A **family** (`family_id` UUID) is created at login; each rotation adds a row to the same family.

### Rotation and reuse detection

```mermaid
sequenceDiagram
    autonumber
    participant C as Client
    participant I as Identity (/api/auth/refresh)
    participant DB as Postgres
    C->>I: POST /refresh (Cookie vcare_rt = T1)
    I->>DB: SELECT … FROM refresh_tokens WHERE token_hash = sha256(T1)
    alt unknown or expired
        I-->>C: 401 RefreshTokenInvalid (clear cookie)
    else rotated < 10 s ago and its successor is still live — GRACE (ADR 0005)
        I-->>C: 401 RefreshTokenInvalid (family NOT revoked, cookie NOT cleared); metric refresh_token_grace_reuse
    else revoked with reason 'rotated' outside the grace rule — REUSE
        I->>DB: BEGIN; UPDATE refresh_tokens SET revoked_at=now(), revoked_reason='reuse_detected' WHERE family_id=F AND revoked_at IS NULL; COMMIT
        I-->>C: 401 RefreshTokenReused (clear cookie); log warn + metric
    else revoked for another reason (logout, status_changed, …)
        I-->>C: 401 RefreshTokenInvalid (clear cookie)
    else live
        I->>DB: SELECT status, role, email_verified_at FROM users WHERE id = user_id AND deleted_at IS NULL
        alt suspended
            I->>DB: revoke family F (reason 'status_changed')
            I-->>C: 403 AccountSuspended (clear cookie)
        else allowed
            I->>DB: BEGIN; SELECT … FOR UPDATE (T1); INSERT T2 (family F); UPDATE T1 SET revoked_at, revoked_reason='rotated', replaced_by_id=T2; COMMIT
            I-->>C: 200 { accessToken } + Set-Cookie vcare_rt = T2
        end
    end
```

- The rotation locks the presented row (`FOR UPDATE`) so two concurrent refreshes with the same token
  cannot both succeed; the loser sees `revoked_reason='rotated'`. If the rotation happened less than
  `REFRESH_REUSE_GRACE_SECONDS` (10 s) ago and the successor is still live, the loser gets `401 RefreshTokenInvalid`
  with **no family revocation and no clearing cookie**, and the client retries once with the successor cookie
  (browsers share one cookie jar across tabs). Otherwise reuse detection revokes the family. If the retry also fails,
  the client calls logout, which revokes the presented token's family. See
  [ADR 0005](../adr/0005-refresh-reuse-grace-window.md).
- The new refresh token's `expires_at` is issue time + 30 days (sliding session); rate limit 30/min per family.
- Budget: p95 < 50 ms (one indexed lookup, one PK read, one short transaction, one EdDSA sign).

## 4. Revocation paths

| Trigger | What is revoked | `revoked_reason` | Same transaction as |
|---|---|---|---|
| `POST /api/auth/logout` | the presented token's family | `logout` | — |
| Reuse detected on refresh | the whole family | `reuse_detected` | — |
| `POST /api/auth/change-password` | every family **except** the cookie's family | `password_changed` | password hash update |
| `POST /api/auth/reset-password` | every family | `password_reset` | password hash update + `used_at` |
| Status → `suspended` or `rejected` (admin or Care) | every family | `status_changed` | status update + `user_status_changes` row |
| Refresh by a suspended user | that family | `status_changed` | — |
| `DELETE /api/users/{id}/sessions` (admin) | every family | `admin_revoked` | — |
| Account soft delete | every family | `account_deleted` | `deleted_at` update |

Revocation is `UPDATE refresh_tokens SET revoked_at = now(), revoked_reason = $r WHERE user_id = $1 AND revoked_at IS NULL`
(or `family_id = $1`), served by partial indexes in [data-model.md](./data-model.md).

## 5. Residual access window (accepted)

Access tokens are verified locally and are not revocable. After any revocation above, an access token
already issued stays valid until its `exp` — **at most 15 minutes**. This is accepted
([ADR 0002](../adr/0002-asymmetric-jwt-rotating-refresh.md)) because:
- the refresh token is dead immediately, so the session cannot be extended;
- Care additionally blocks suspended doctors **locally at once** when it decides the suspension (Case 3);
- the alternative (per-request introspection) makes Identity a synchronous dependency of every Care
  request, which PRD §4.4 rules out.

Identity's own `user-guard` trusts the token's `status` claim; routes that must see the live status
(refresh, login, admin status change) re-read the user row.

## 6. Password handling (summary)
argon2id (`memoryCost=19456 KiB, timeCost=2, parallelism=1`); legacy bcrypt verified then rehashed on
login; 10..128 chars; breached-password denylist; dummy argon2 verify for unknown emails; never logged or
compared with `===`. Rationale: [ADR 0003](../adr/0003-argon2id-password-hashing.md).

## 7. One-time secrets
| Kind | Format | TTL | Storage | Single use | On reissue |
|---|---|---|---|---|---|
| Registration code (ADR 0006) | 6 digits (CSPRNG) | 10 min from send, max 5 attempts | `registration_challenges.code_hash` = HMAC-SHA256(`OTP_PEPPER`, code), hex | `consumed_at` (same transaction as the `users` insert) | a new `register/start` sets `invalidated_at` on open challenges; the 5th failed attempt invalidates too |
| Password reset | 256-bit random | 30 min from send | `password_resets.token_hash` (sha256) | `used_at` | earlier unused tokens get `invalidated_at` |

Both secrets are **generated by the outbox worker at send time** (ADR 0007): the request only creates the row and
the job; the worker writes the hash and `expires_at`, and the plaintext exists only in worker memory and the email.
Registration codes are compared in constant time against the latest open challenge for the email; reset tokens by
hash lookup. `register/start` and forgot-password always return a uniform response (`202` / `204`). Accounts are
created already verified, so there is no separate verify-email flow.
