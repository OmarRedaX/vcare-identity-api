## High
- [x] RESOLVED (verified 2026-10-05) — login locks and re-reads the live user before inserting a refresh token; a changed hash or soft-deleted row returns `401 InvalidCredentials`, and a newly suspended row returns `403 AccountSuspended` (src/app/auth/service/session.service.ts:98-128; src/app/auth/repository/user.repo.ts:72-85; tests/integration/auth/sessions.test.ts:274-309; tests/unit/app/auth/session.service.test.ts:219-253)
  - Original: [High][CONFIRMED] Login can issue a new session after a password reset · `src/app/auth/service/session.service.ts:64-128`
  - Scenario: login verifies the old password, then a password reset or suspension commits before login inserts its refresh token. Without a locked re-read, the stale verification can create a live session after reset or suspension; a soft-deleted account can also pass the earlier read.
  - Rule: CLAUDE.md -> Domain rules (entering `suspended` revokes refresh tokens; password reset revokes all families).
  - Fix: inside the login transaction, `SELECT … FOR UPDATE` the live user by id before token insertion; refuse a missing row or changed password hash with `InvalidCredentials`, or a suspended row with `AccountSuspended`. Signing uses the locked row.
  - Test gap: closed by two integration race tests (`tests/integration/auth/sessions.test.ts:274-309`) and three unit tests for changed hash, soft deletion, and suspension (`tests/unit/app/auth/session.service.test.ts:219-253`).

## Medium
- [x] RESOLVED (verified 2026-10-04) — capture now completes on the handler's `res.end` (not socket close), so the outcome is stored after a disconnect and the in-flight key is kept (deleted only for 5xx/429); unit test rewritten, integration test aborts mid-flight, sees 409 meanwhile, then a replayed 201 (src/lib/idempotency/idempotency.ts:93-130; tests/integration/idempotency.test.ts, tests/unit/lib/idempotency/idempotency.test.ts)
  - Original: [Medium][CONFIRMED] Idempotency middleware discards the key on client disconnect while the handler keeps running and commits · `src/lib/idempotency/idempotency.ts:122-126,197-201`
  - Scenario: client POSTs `register/complete`, disconnects before the 201 is written. `res` emits `close` with `writableEnded=false`, so `clientClosed=true` and the key is deleted. Express does not abort the handler, so the account is created and the challenge consumed. The retry with the same key and body re-runs the handler and gets `400 ValidationFailed field=code` instead of the replayed 201. A concurrent retry arriving while the first handler is still running also finds no key and starts a second handler instead of getting 409.
  - Rule: CLAUDE.md -> API conventions (Idempotency: same key + same body replays the original; in-flight -> 409).
  - Fix: on client close, leave the in-flight record to be overwritten by the handler's outcome. The handler still ends the response, so store the result on completion even when the socket is gone, and delete only for 5xx/429. Otherwise keep the in-flight key until `IN_FLIGHT_TTL_MS`.
  - Test gap: integration test that aborts the request mid-flight, then retries with the same key and body and expects the replayed 201.
