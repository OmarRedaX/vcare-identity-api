# auth — Spec

Scope source: [brainstorm.md](./brainstorm.md). Binding rules: `CLAUDE.md` (cited by section name). Source of truth
for every HTTP shape: `contracts/openapi.yaml` (operations `startRegistration`, `completeRegistration`, `login`,
`refreshAccessToken`, `logout`, `forgotPassword`, `resetPassword`, `changePassword`, `getMe`, `updateMe`, `getJwks`).
Foundation APIs this spec builds on: [foundation/spec.md](../foundation/spec.md) (§15 wins over §1–14).

**Status: ready.** Open questions is empty (section 14). The three v1.0.0 questions were decided by the user on
2026-09-17 and folded into the body: login accepts no `Idempotency-Key` (D-1), change-password gains a per-user
limiter and a `429` (D-2), and password reset uses a **typed 6-digit code** instead of an emailed link token (D-3),
mirroring the registration challenge exactly. The decisions and their rationale are recorded in 14.1. The contract
edits in 14.2 are a **prerequisite**: `/develop` applies them to `contracts/openapi.yaml` as build step 0 before
writing code (CLAUDE.md → Build order for a new module).

### 1.2 Principles
1. **Contract first.** Every status, error code, header, and body matches `contracts/openapi.yaml`. Where the contract
   is internally inconsistent this spec follows the operation's own prose and lists the fix in 14.2.
2. **Identity only from a verified token or the refresh cookie.** Never from headers, body, or path.
3. **Deny by default.** Every route declares `authorize(policy)`, including public ones; the app refuses to boot
   if a route lacks it (4.2).
4. **Secrets are hashes at rest** — argon2id passwords, sha256 refresh tokens, HMAC-SHA256 registration and
   password-reset codes. One-time secrets are generated by the worker at send time; outbox rows hold ids only.
5. **Uniform responses on public account-probing routes:** `register/start` always `202`, `forgot-password` always
   `204`, login always `401 InvalidCredentials` for unknown email or wrong password (with a dummy argon2 verify), and
   `reset-password` always the same `400 ValidationFailed field=code` whether the email is unknown or the code wrong
   (with the argon2 hash computed on every path).
6. **The service owns transactions**; repositories take `conn: Knex = db`; argon2 never runs while a transaction or
   pooled connection is held.
7. **Hot paths stay small:** login (1 read + 1 short tx), refresh (1 read + 1 Redis call + 1 short tx), JWKS
   (memory only). No outbound network call on any request path.
8. **Redis is Tier 2** (ADR 0008): credential limiters fall back in-process, refresh limiter fails open, idempotency
   is skipped and database constraints stop duplicates.

### 1.3 Dependencies
- **foundation** (built): error envelope, `validateBody`, `sendSuccess`/`sendNoContent`/`sendRaw`, `sealRouter`,
  `noStore`, `clientIp`, `rateLimit`, `idempotency`, `db`, `redis`, `logger` + `metric`, `requestContext`,
  `runLoop`, DI container and `registerDependencies(overrides)`, test helpers.
- **New runtime dependencies:** `jose` (EdDSA JWT/JWK), `argon2` (argon2id), `bcrypt` (legacy verify only). All
  three are in CLAUDE.md → Tech stack (locked); following the ADR 0015 precedent the developer writes
  **ADR 0016 — auth runtime dependencies** before installing them (content: 12.1). No cookie parser, no Resend SDK,
  no `node-fetch`: cookies are parsed in `lib/http/cookies.ts`, email uses Node 24 global `fetch`.
- **Consumers of this module:** `users` (Epic A, next) — see 1.4. Epic B (`service-auth`, `internal-users`) reuses
  `lib/auth/jwt.ts` (service tokens), `lib/rbac` (a `service` policy kind), `SessionService.revokeAllForUser`, and
  `AccountService`.
- **Other services:** none called. care-service consumes `GET /.well-known/jwks.json` and the access-token claims
  (section 6).

### 1.4 Module boundaries (decisions)
- **`auth` owns the `users` table repository** (`src/app/auth/repository/user.repo.ts`) and the `User` entity, so
  there is exactly one column list and one row mapper for `users`. The `users` module (Epic A, next) and Epic B read
  and write `users` **only through `AccountService`** methods; the `users` spec adds the functions it needs (admin
  keyset list, lock-for-update, status update) to `user.repo.ts` and `AccountService`, together with its own
  migration for the `idx_users_*_created_at_id` indexes (those indexes serve queries that do not exist in `auth`, so
  `auth` does not create them — CLAUDE.md → Database rules).
- **`auth` owns `refresh_tokens`** and exposes revocation through `SessionService`:
  - `revokeAllForUser(conn: Knex, userId: number, reason: RevokedReason): Promise<number>` — used here by reset
    and change-password, and by `users` (`status_changed`, `admin_revoked`) inside the caller's transaction.
  - `users` adds `listLiveFamilies(userId, cursor, limit)` to `SessionService` in its own unit. Note for the users
    spec: the shared cursor (`lib/http/pagination/cursor.ts`) rejects a non-integer tiebreaker, so the contract's
    `(created_at DESC, family_id)` keyset needs a cursor extension or a numeric tiebreaker (the family's first token
    `id`) — decided in the users spec.
- `user_status_changes` is not created here (owned by `users`). Registration's initial status is not a status change.
- The module deliberately has several service, repository, and controller files (one per bounded sub-area) instead
  of the single `<module>.service.ts` skeleton; each file still holds one class or one set of repository functions.

## 2. Database schema

Five raw-SQL migrations (`write-migration` skill), applied in this order after
`20260915000000_create_citext_extension.ts`. Every `up` has a real `down` (`DROP TABLE IF EXISTS … ;` in reverse).
Tables `refresh_tokens`, `password_resets`, `registration_challenges`, `outbox_jobs` are **token/job tables**, not
business tables: they have no `deleted_at` and are purged by the worker with `DELETE` (data-model.md → Conventions;
CLAUDE.md → Database rules forbids `DELETE` on business tables only). `users` is the only business table here.

### 2.1 `20260917000100_create_users.ts`
```sql
CREATE TABLE users (
  id                 BIGSERIAL PRIMARY KEY,
  email              CITEXT        NOT NULL,
  phone              VARCHAR(16)   NULL,
  password_hash      VARCHAR(255)  NOT NULL,
  full_name          VARCHAR(120)  NOT NULL,
  avatar_url         VARCHAR(2048) NULL,
  role               VARCHAR(16)   NOT NULL,
  status             VARCHAR(16)   NOT NULL,
  email_verified_at  TIMESTAMPTZ   NULL,
  timezone           VARCHAR(64)   NOT NULL,
  locale             VARCHAR(35)   NOT NULL,
  created_at         TIMESTAMPTZ   NOT NULL DEFAULT now(),
  updated_at         TIMESTAMPTZ   NOT NULL DEFAULT now(),
  deleted_at         TIMESTAMPTZ   NULL,
  CONSTRAINT chk_users_role   CHECK (role IN ('patient','doctor','admin')),
  CONSTRAINT chk_users_status CHECK (status IN ('pending','active','suspended','rejected')),
  CONSTRAINT chk_users_phone_e164 CHECK (phone IS NULL OR phone ~ '^\+[1-9][0-9]{7,14}$'),
  CONSTRAINT chk_users_full_name_not_blank CHECK (length(btrim(full_name)) > 0),
  CONSTRAINT chk_users_email_length CHECK (length(email) <= 254)
);
-- login, register/start, register/complete, forgot-password: WHERE email = $1 AND deleted_at IS NULL
CREATE UNIQUE INDEX uq_users_email ON users (email) WHERE deleted_at IS NULL;
```
No default on `role`/`status`. By-id reads (`getMe`, `updateMe`, refresh user re-read, change-password) use the PK.

### 2.2 `20260917000200_create_refresh_tokens.ts`
```sql
CREATE TABLE refresh_tokens (
  id              BIGSERIAL PRIMARY KEY,
  user_id         BIGINT       NOT NULL,
  family_id       UUID         NOT NULL,
  token_hash      CHAR(64)     NOT NULL,
  expires_at      TIMESTAMPTZ  NOT NULL,
  revoked_at      TIMESTAMPTZ  NULL,
  revoked_reason  VARCHAR(32)  NULL,
  replaced_by_id  BIGINT       NULL,
  device_info     VARCHAR(255) NULL,
  created_at      TIMESTAMPTZ  NOT NULL DEFAULT now(),
  CONSTRAINT fk_refresh_tokens_user_id FOREIGN KEY (user_id) REFERENCES users (id),
  CONSTRAINT fk_refresh_tokens_replaced_by_id FOREIGN KEY (replaced_by_id) REFERENCES refresh_tokens (id) ON DELETE SET NULL,
  CONSTRAINT chk_refresh_tokens_revoked_reason CHECK (revoked_reason IS NULL OR revoked_reason IN
    ('rotated','reuse_detected','logout','password_changed','password_reset','status_changed','admin_revoked','account_deleted')),
  CONSTRAINT chk_refresh_tokens_revoked_pair CHECK ((revoked_at IS NULL) = (revoked_reason IS NULL)),
  CONSTRAINT chk_refresh_tokens_replaced_by_rotated CHECK (replaced_by_id IS NULL OR revoked_reason = 'rotated'),
  CONSTRAINT chk_refresh_tokens_token_hash_hex CHECK (token_hash ~ '^[0-9a-f]{64}$'),
  CONSTRAINT chk_refresh_tokens_expiry CHECK (expires_at > created_at)
);
-- refresh / logout / change-password cookie lookup: WHERE token_hash = $1 (includes revoked rows so reuse is detectable)
CREATE UNIQUE INDEX uq_refresh_tokens_token_hash ON refresh_tokens (token_hash);
-- covers fk_refresh_tokens_user_id; revoke-all for a user: UPDATE … WHERE user_id = $1 AND revoked_at IS NULL [AND family_id <> $2]
-- (reset, change-password, users module suspension / admin revoke); users module session list by user
CREATE INDEX idx_refresh_tokens_user_id_created_at ON refresh_tokens (user_id, created_at DESC);
-- revoke a family: UPDATE … WHERE family_id = $1 AND revoked_at IS NULL (logout, reuse detection, suspended refresh)
CREATE INDEX idx_refresh_tokens_family_id_live ON refresh_tokens (family_id) WHERE revoked_at IS NULL;
-- covers fk_refresh_tokens_replaced_by_id (ON DELETE SET NULL during purge); enforces one successor per token
CREATE UNIQUE INDEX uq_refresh_tokens_replaced_by_id ON refresh_tokens (replaced_by_id) WHERE replaced_by_id IS NOT NULL;
-- worker purge: DELETE … WHERE id IN (SELECT id … WHERE expires_at < now() - interval '30 days' LIMIT $n)
CREATE INDEX idx_refresh_tokens_expires_at ON refresh_tokens (expires_at);
```
Decisions vs data-model.md (doc fixes in 12.2):
- One full `(user_id, created_at DESC)` index replaces the partial `idx_refresh_tokens_user_id_live` **plus** the
  plain `idx_refresh_tokens_user_id`: it covers the FK and serves revoke-all; per-user row counts are bounded by
  retention, and the table is write-hot (every refresh inserts), so one index instead of two.
- `replaced_by_id` is unique (1:1 successor, matches the ERD) and `ON DELETE SET NULL` so purge batches can never
  fail on the self-reference. No `ON DELETE` on `user_id` (users are never hard-deleted).
- Retention is measured from `expires_at` only: every row expires at most 30 days after issue, so a revoked row is
  kept at most 30 days past its expiry. One purge index, no `revoked_at` index.

### 2.3 `20260917000300_create_password_resets.ts`
Password reset is a **typed 6-digit code**, structurally identical to the registration challenge (D-3), so this
table mirrors `registration_challenges`: `code_hash` (HMAC-SHA256 with `OTP_PEPPER`) plus an `attempts` counter.
```sql
CREATE TABLE password_resets (
  id              BIGSERIAL PRIMARY KEY,
  user_id         BIGINT       NOT NULL,
  code_hash       CHAR(64)     NULL,
  attempts        SMALLINT     NOT NULL,
  expires_at      TIMESTAMPTZ  NULL,
  used_at         TIMESTAMPTZ  NULL,
  invalidated_at  TIMESTAMPTZ  NULL,
  created_at      TIMESTAMPTZ  NOT NULL DEFAULT now(),
  CONSTRAINT fk_password_resets_user_id FOREIGN KEY (user_id) REFERENCES users (id),
  CONSTRAINT chk_password_resets_code_sent CHECK ((code_hash IS NULL) = (expires_at IS NULL)),
  CONSTRAINT chk_password_resets_attempts CHECK (attempts BETWEEN 0 AND 5),
  CONSTRAINT chk_password_resets_code_hash_hex CHECK (code_hash IS NULL OR code_hash ~ '^[0-9a-f]{64}$'),
  CONSTRAINT chk_password_resets_used_after_sent CHECK (used_at IS NULL OR code_hash IS NOT NULL),
  CONSTRAINT chk_password_resets_single_end CHECK (used_at IS NULL OR invalidated_at IS NULL)
);
-- covers fk_password_resets_user_id; reset-password: latest open row for the user
--   SELECT <PASSWORD_RESET_COLUMNS> FROM password_resets
--   WHERE user_id = $1 AND used_at IS NULL AND invalidated_at IS NULL
--   ORDER BY created_at DESC LIMIT 1 FOR UPDATE;
-- forgot-password / reset: invalidate open rows — UPDATE … WHERE user_id = $1 AND used_at IS NULL AND invalidated_at IS NULL
CREATE INDEX idx_password_resets_user_id_created_at ON password_resets (user_id, created_at DESC);
-- worker purge: WHERE created_at < now() - interval '30 days'
CREATE INDEX idx_password_resets_created_at ON password_resets (created_at);
```
Decisions:
- **No unique index on `code_hash`.** A 6-digit code is not globally unique, so uniqueness would be wrong (two users
  can legitimately hold the same code) and the lookup is no longer by hash: reset resolves the user by email among
  live rows (`uq_users_email`), then takes that user's latest open row `FOR UPDATE`. `uq_password_resets_token_hash`
  from the v1.0.0 draft and from `data-model.md` is therefore **dropped** (doc fix 12.2).
- **One full composite index** `idx_password_resets_user_id_created_at (user_id, created_at DESC)` serves both the
  latest-open lookup (with the open predicate as a filter) and the invalidation `UPDATE`, and **covers the FK** as
  CLAUDE.md → Database rules requires — a partial `WHERE used_at IS NULL AND invalidated_at IS NULL` index would not.
  Rows per user are bounded (forgot-password is 3/h per email and purge removes rows after 30 days), so the open row
  is the first index entry read in practice. Same rationale as `idx_refresh_tokens_user_id_created_at` (2.2).
- **`attempts` has no default**; the repository inserts `0` explicitly, exactly as for `registration_challenges`.
- **Purge by `created_at + 30 days`** is unchanged and still coherent: a code expires 30 minutes after send and can
  only be used before expiry, so a 30-day-old row is always terminal. One purge index.

### 2.5 `20260917000500_create_outbox_jobs.ts`
```sql
CREATE TABLE outbox_jobs (
  id            BIGSERIAL PRIMARY KEY,
  type          VARCHAR(48)  NOT NULL,
  aggregate_id  BIGINT       NOT NULL,
  status        VARCHAR(16)  NOT NULL,
  attempts      SMALLINT     NOT NULL,
  run_after     TIMESTAMPTZ  NOT NULL,
  locked_until  TIMESTAMPTZ  NULL,
  last_error    VARCHAR(500) NULL,
  request_id    UUID         NOT NULL,
  created_at    TIMESTAMPTZ  NOT NULL DEFAULT now(),
  updated_at    TIMESTAMPTZ  NOT NULL DEFAULT now(),
  completed_at  TIMESTAMPTZ  NULL,
  CONSTRAINT chk_outbox_jobs_type CHECK (type IN ('send_registration_code','send_account_exists_notice','send_password_reset')),
  CONSTRAINT chk_outbox_jobs_status CHECK (status IN ('pending','processing','done','dead')),
  CONSTRAINT chk_outbox_jobs_attempts CHECK (attempts >= 0),
  CONSTRAINT chk_outbox_jobs_lease CHECK ((status = 'processing') = (locked_until IS NOT NULL)),
  CONSTRAINT chk_outbox_jobs_completed CHECK ((status IN ('done','dead')) = (completed_at IS NOT NULL))
);
-- worker claim: WHERE status = 'pending' AND run_after <= now() ORDER BY run_after LIMIT $n FOR UPDATE SKIP LOCKED;
-- lag metric: SELECT min(run_after) … WHERE status = 'pending' AND run_after <= now()
CREATE INDEX idx_outbox_jobs_run_after_pending ON outbox_jobs (run_after) WHERE status = 'pending';
-- lease reclaim: WHERE status = 'processing' AND locked_until < now() … FOR UPDATE SKIP LOCKED
CREATE INDEX idx_outbox_jobs_locked_until_processing ON outbox_jobs (locked_until) WHERE status = 'processing';
-- worker purge: done after 7 days, dead after 30 days, by completed_at
CREATE INDEX idx_outbox_jobs_completed_at ON outbox_jobs (status, completed_at) WHERE status IN ('done','dead');
```
`aggregate_id` is a logical reference (no FK, no index — nothing queries by it). Rows never hold PII or secrets;
`last_error` holds an error class name only (≤ 64 chars in practice).

### 2.6 Timestamp ownership
| Column | Set by |
|---|---|
| `created_at` | column default `now()` (transaction time) |
| `users.updated_at` | repository, `now()` on every update |
| `users.email_verified_at` | `register/complete` tx, `now()` |
| `refresh_tokens.expires_at` | service, `addTime(clock.now(), 30, "d")` |
| `refresh_tokens.revoked_at`, `password_resets.used_at/invalidated_at`, `registration_challenges.consumed_at/invalidated_at` | SQL `now()` in the same statement as the state change |
| `registration_challenges.expires_at` / `password_resets.expires_at` | worker at send time: `now() + interval '10 minutes'` / `'30 minutes'` in SQL |
| `outbox_jobs.run_after/locked_until/updated_at/completed_at` | SQL `now()` ± intervals computed by `lib/outbox/backoff.ts` |

Expiry comparisons in SQL use `now()`; comparisons in services use the injected `Clock` and `isPast`. Integration
tests that need expiry move rows' timestamps backwards with a test-only SQL helper rather than faking `now()` in
Postgres.

**Custom validators**
- `IsIanaTimeZone`: valid when `new Intl.DateTimeFormat("en-US", { timeZone: value })` does not throw; a transform

  `must be a valid IANA time zone`.
- `IsBcp47Locale`: valid when `Intl.getCanonicalLocales(value)` returns exactly one tag; the stored value is that
  canonical tag (`ar-eg` → `ar-EG`). Issue: `must be a valid BCP-47 language tag`.
- `IsNotBlank`: `value.trim().length > 0` (otherwise `chk_users_full_name_not_blank` would raise a 500). Issue:
  `must not be blank`.
- `IsAcceptablePassword`: `!PASSWORD_DENYLIST.has(value.toLowerCase())`. Issue: `is too common`.
- `MinProperties(n)`: class-level check on the raw body's own key count.

### 3.6 Response DTOs (`dto/auth.response.dto.ts`)
- `UserResponseDto.from(user)` → `{ id, email, phone, fullName, avatarUrl, role, status, emailVerifiedAt, timezone, locale, createdAt, updatedAt }`:
  exactly the 12 required `User` properties; dates as ISO-8601 UTC strings; nullable fields as `null`. Never
  `passwordHash` or `deletedAt`. Viewer-aware rendering is not needed: Identity holds no clinical data, and the
  caller is the owner (`/me`) or the anonymous registrant of this very account (`register/complete`).
- `AccessTokenResponseDto.from(accessToken)` → `{ accessToken, tokenType: "Bearer", expiresIn: 900 }`.
- `LoginResponseDto.from(accessToken, user)` → `{ accessToken, tokenType: "Bearer", expiresIn: 900, user }`.

The refresh token is **never** in a body — only in `Set-Cookie`.

### 3.8 Services and transaction boundaries
All services are `@injectable()` with explicit `@inject(TOKENS.X)` on every constructor parameter (ADR 0015).
Injected: `Db`, `Logger`, `Clock`, `PasswordHasher`, `TokenSigner`, `Env`, `OutboxEnqueuer` (lib function wrapper),
`RateLimiter` (for refresh) as needed. Argon2 work (hash/verify) always runs **before** a transaction opens.

**`RegistrationService`**
- `start(email, requestId)`: one tx — `findLiveByEmail(email, trx)`; known → `enqueue(trx, "send_account_exists_notice", user.id)`;
  unknown → `invalidateOpenForEmail`, `insertChallenge`, `enqueue(trx, "send_registration_code", challengeId)`.
  Returns nothing; log `registration_start_accepted` (no email, no outcome).
- `complete(input, requestId)`:
  1. `hash = await hasher.hash(input.password)` (semaphore; queue full → `429 RateLimited`).
  2. tx: `challenge = findLatestOpenForUpdate(email)`. Check, in order: none → `no_challenge`; `codeHash` null →
     `not_sent`; `isPast(expiresAt)` → `expired`; `timingSafeEqualHex(hmacSha256Hex(OTP_PEPPER, code), codeHash)`
     false → `recordFailedAttempt(id, exhausted = attempts + 1 >= 5)` → `mismatch`/`exhausted`; true →
     `markConsumed` then `insertUser({ email, phone ?? null, passwordHash: hash, fullName, role, status: role === "doctor" ? "pending" : "active", timezone, locale })`.
  3. Commit happens for every outcome except a unique violation; after commit, anything other than `match` throws
     `InvalidRegistrationCode` (so the attempt counter persists). Postgres `23505` on `uq_users_email` → rollback →
     `EmailAlreadyRegistered` (409; challenge stays unconsumed).
  4. Log `registration_code_failed { challengeId, attempts, exhausted }` or `user_registered { userId, role, status }`.
- The user is not logged in (no cookie, no token).

**`SessionService`**
- `login(input)`:
  1. `user = findLiveByEmail(email)` (no tx).
  2. none → `hasher.verifyDummy(password)` → throw `InvalidCredentials`; log `login_failed { reason: "unknown_email" }`, metric `login_failed`.
  3. `{ ok, needsRehash } = hasher.verify(user.passwordHash, password)`; not ok → `InvalidCredentials`,
     `login_failed { userId, reason: "wrong_password" }`, metric.
  4. `user.status === "suspended"` → `AccountSuspended`; log `login_refused_suspended { userId }`. (Checked only
     after the password is verified, so status is never revealed without the password.)
  5. `needsRehash` → `newHash = hasher.hash(password)`; a full hash queue skips the rehash (`password_rehash_skipped`), never failing the login.
  6. tx: optional `updatePasswordHash`; `refreshToken = randomToken()`; `insertToken({ userId, familyId: randomUuid(), tokenHash: sha256Hex(refreshToken), expiresAt: addTime(now, 30, "d"), deviceInfo })`;
     `accessToken = signer.signUserToken(user)`; commit. Log `login_succeeded { userId }`.
  - `deviceInfo` = `User-Agent` with control characters removed, truncated to 255 characters, `null` if absent.
- `refresh(presentedToken, rateLimiter)` → `RefreshOutcome` (algorithm in 4.4).
- `logout(presentedToken | undefined)`: if the cookie value matches `^[A-Za-z0-9_-]{43}$`: `token = findByTokenHash(sha256Hex)`;
  if found: `revokeFamily(token.familyId, "logout")` (revokes every still-live row of the family, whatever the
  presented row's state). Log `logout { userId }` when found. Never throws for cookie problems.
- `revokeAllForUser(conn, userId, reason)`: `refresh-token.repo.revokeAllForUser`; returns count. Callers pass their
  transaction.
- `revokeAllExceptFamily(conn, userId, familyId | undefined, reason)`.

**`PasswordService`**
- `forgot(email, requestId)`: `user = findLiveByEmail(email)` (any status, including `suspended` — the contract
  allows a suspended account to reset); none → return. Else one tx: `invalidateOpenForUser`, `insertReset`,
  `enqueue("send_password_reset", resetId)`. Log `password_reset_requested` (no ids that map to the email are
  needed; `userId` is logged).
- `reset(input: ResetPasswordInput)` — the registration-complete algorithm with the user resolved by email first:
  1. `hash = await hasher.hash(input.newPassword)` (semaphore; queue full → `429 RateLimited`). **Always**, for every
     outcome, before the transaction opens: the argon2 hash dominates the response time, so an unknown email costs
     the same as a wrong code (enumeration safety, BR-20a).
  2. tx:
     a. `user = findLiveByEmail(input.email, trx)`.
     b. `reset = user ? findLatestOpenForUpdate(user.id, trx) : undefined`.
     c. Check, in order: no `user` or no `reset` → `no_reset`; `codeHash` null → `not_sent`; `isPast(expiresAt)` →
        `expired`; `timingSafeEqualHex(hmacSha256Hex(OTP_PEPPER, input.code), reset.codeHash)` false →
        `recordFailedAttempt(reset.id, exhausted = reset.attempts + 1 >= 5)` → `mismatch`/`exhausted`; true → `match`.
     d. `match` → `updatePasswordHash(user.id, hash, trx)` (0 rows → outcome becomes `no_reset`); `markUsed(reset.id, trx)`
        (0 rows → throw, rollback, 500 — the row is locked, so this cannot happen); `invalidateOpenForUser(user.id, trx)`
        (any other open rows); `revokedSessions = sessions.revokeAllForUser(trx, user.id, "password_reset")`.
     e. Commit for **every** outcome (so a failed attempt's counter persists, exactly as in `register/complete`).
  3. When there is no candidate row (`no_reset`, `not_sent`), a dummy `hmacSha256Hex(OTP_PEPPER, input.code)` against a
     constant 64-hex string is computed and discarded, so the same HMAC + constant-time compare work happens on every
     path.
  4. Outcome ≠ `match` → throw `InvalidResetCode` (identical `400` body for all six failure reasons).
  5. Log `password_reset_failed { resetId?, attempts?, outcome }` (warn, never the email) or
     `password_reset_completed { userId, revokedSessions }`.
- `change(input)`:
  1. `user = findLiveById(userId)`; none → `Unauthorized`; `suspended` → `AccountSuspended`.
  2. `verify(user.passwordHash, currentPassword)` not ok → `InvalidCredentials`; log `password_change_failed { userId }`.
  3. `hash = hasher.hash(newPassword)`.
  4. `keepFamily`: when the `vcare_rt` cookie is a well-formed token whose row exists **and belongs to this user**,
     its `familyId`; otherwise `undefined` (all families revoked).
  5. tx: `updatePasswordHash` (0 rows → `Unauthorized`); `revokeAllExceptFamily(trx, userId, keepFamily, "password_changed")`; commit.
  6. Log `password_changed { userId, revokedSessions, keptCurrentSession }`.

**`AccountService`**
- `getMe(userId)`: `findLiveById`; none → `Unauthorized` (soft-deleted or unknown subject); `suspended` →
  `AccountSuspended`; else `User`.
- `updateMe(userId, patch)`: `updateProfileUnlessSuspended`; a returned row → `User`, log `profile_updated { userId, fields }`
  (field names only). No row → `findLiveById`: none → `Unauthorized`; suspended → `AccountSuspended`.
- `findLiveById(userId, conn?)`: for `users` and Epic B.

**`AuthMailService`** (worker only; 5.5) and **`PurgeService`** (worker only; 5.6).

Suspended-with-live-access-token (brainstorm open question 3) is **resolved without extra cost**: every self route
already reads the user row by PK, and the service rejects `suspended` from that row, so the contract's
`AccountSuspended` is enforced within the 15-minute residual window.

## 4. API contract

### 4.1 Mounting and middleware order
- `src/routes.ts`: `router.use("/auth", buildAuthRouter(scope))` → served at `/api/auth/*`.
- `src/app.ts`: `app.use("/.well-known", buildWellKnownRouter(scope))` **before** `/api` (the JWKS path is not under
  `/api`). Both builders live in `src/app/auth/routes.ts` and return `sealRouter(router)`.
- `buildAuthRouter` starts with `router.use(noStore())`, so **every** `/api/auth/*` response — success, error,
  429, and unmatched `/api/auth/*` 404 — carries `Cache-Control: no-store`.
- Per-route order: `rateLimit(...)` (public and cookie routes) → `userGuard` (bearer routes) → `authorize(policy)` →
  `rateLimit(...)` keyed by user (change-password only, D-2 — the subject is the authenticated user id, so it must run
  after the guard) → `idempotency(...)` → controller method.
  Limiters on public routes run before validation and hashing (CLAUDE.md → Security rules).
- Controllers: validate → call service → `sendSuccess` / `sendNoContent` / `sendAccepted` / `sendRaw`; cookie
  headers are set by the controller through `lib/http/cookies.ts` from the service result. No business logic.
- `X-Request-Id` is added to every response by the foundation middleware.

### 4.2 RBAC — policy types, `authorize`, and the boot check
`src/lib/rbac/types.ts`:
```ts
export type Role = "patient" | "doctor" | "admin";
export type AccountStatus = "pending" | "active" | "suspended" | "rejected";
export type Policy =
  | { kind: "public"; owner: "none" }                                     // no principal
  | { kind: "refresh-cookie"; roles: readonly Role[]; owner: "refresh-family" } // principal = the cookie's token row, resolved in SessionService
  | { kind: "user"; roles: readonly Role[]; owner: "self" | "none"; allowedStatuses: readonly AccountStatus[] };
// Epic B adds { kind: "service"; scope: string; owner: "none" }.
```
`src/lib/rbac/authorize.ts` — `authorize(policy: Policy | undefined): RequestHandler`:
- `policy` undefined → throws at router construction (`route_without_policy`), so the process never starts.
- `public` and `refresh-cookie` → `next()` (no bearer principal is required; `refresh-cookie` ownership and roles are
  enforced by `SessionService`, which only acts on the family of the presented token and checks the owner's role
  against `policy.roles`).
- `user`: `req.auth?.kind !== "user"` → `Unauthorized`; role not in `roles` → `Forbidden`; `status` claim not in
  `allowedStatuses` → `AccountSuspended` when `suspended`, else `Forbidden`. Ownership `self`: the route has no id
  parameter — the service acts only on `req.auth.userId`, so the predicate is satisfied by construction and a
  non-owner cannot even name another resource. `none` → role check only.
- A denial logs `access_denied { reason: "role" | "status" | "unauthenticated" }` at `info` (no ids from the request).
- The returned handler carries a non-enumerable `Symbol.for("vcare.authorize")` marker.

`src/lib/rbac/assert-routes-authorized.ts` — `assertRoutesAuthorized(router, basePath)`: walks the Express 5 router
stack recursively; every layer with a `route` must have a handler with the marker in its stack; routers marked with
`Symbol.for("vcare.probe-exempt")` (the health router, ADR 0014) are skipped. Called at the end of `createApp` on the
routers from `buildPublicRouter` and `buildWellKnownRouter`, and in `createInternalApp` on `buildInternalRouter`; a
violation throws `Error("route_without_policy: <METHOD> <path>")` in every environment. Test-only
`extraApiRouter`/`extraInternalRouter` are not checked.

`src/app/auth/policies.ts`:
| Policy | Value | Routes |
|---|---|---|
| `publicPolicy` | `{ kind: "public", owner: "none" }` | register/start, register/complete, login, forgot-password, reset-password, JWKS |
| `refreshFamilyPolicy` | `{ kind: "refresh-cookie", roles: ["patient","doctor","admin"], owner: "refresh-family" }` | refresh, logout |
| `selfPolicy` | `{ kind: "user", roles: ["patient","doctor","admin"], owner: "self", allowedStatuses: ["pending","active","rejected"] }` | change-password, GET/PATCH me |

`src/lib/auth/user-guard.ts` — `userGuard(deps)`: reads `Authorization`; must be exactly `Bearer <token>`
(case-insensitive scheme, one space); missing/malformed → `Unauthorized`. `verifyUserAccessToken` (5.1) →
`JWTExpired` → `TokenExpired`; any other failure → `Unauthorized`. On success sets
`req.auth = { kind: "user", userId, role, status, ev }` and `getRequestContext().userId = userId` so every later log
line carries `userId`. The guard never reads the database. `UserAuth` in `src/lib/types/types.ts` narrows `role` to
`Role` and `status` to `AccountStatus`.

### 4.4 Refresh algorithm (`SessionService.refresh`)
Inputs: cookie value `t` (may be absent), `now = clock.now()`, `grace = REFRESH_REUSE_GRACE_SECONDS`.
1. `t` absent or not `^[A-Za-z0-9_-]{43}$` → **invalid** (401 `RefreshTokenInvalid`, clear cookie).
2. `row = findByTokenHash(sha256Hex(t))`; none → **invalid**.
3. `consumeRateLimit({ name: "refresh-family", limit: 30, windowMs: 60 000, degrade: "fail-open" }, row.familyId)`;
   denied → **rate_limited** (429, `Retry-After`, cookie untouched).
4. `row.revokedAt` set:
   - `revokedReason === "rotated"` and `revokedAt > subtractTime(now, grace, "s")` and successor
     (`findById(row.replacedById)`) exists, is not revoked, and is not expired → **grace**: 401
     `RefreshTokenInvalid`, **no `Set-Cookie`**, family untouched; log `refresh_token_grace_reuse { userId }` (info),
     metric `refresh_token_grace_reuse`.
   - `revokedReason === "rotated"` otherwise → `revokeFamily(row.familyId, "reuse_detected")` → **reused**: 401
     `RefreshTokenReused`, clear cookie; log `refresh_token_reuse_detected { userId, familyId }` (warn), metric.
   - any other reason → **invalid**.
5. `isPast(row.expiresAt, now)` → **invalid**.
6. Transaction:
   a. `locked = findByIdForUpdate(row.id)`; if `locked.revokedAt` is now set (a concurrent refresh won) → rollback
      and re-run step 4 with `locked` (typically **grace**).
   b. `user = findLiveById(row.userId, trx)`; none → rollback → **invalid**.
   c. `user.status === "suspended"` → `revokeFamily(row.familyId, "status_changed", trx)`, commit → **suspended**:
      403 `AccountSuspended`, clear cookie; log `refresh_refused_suspended { userId }`.
   d. `user.role` not in `refreshFamilyPolicy.roles` → rollback → **invalid** (unreachable under `chk_users_role`).
   e. `next = randomToken()`; `newId = insertToken({ userId, familyId: row.familyId, tokenHash: sha256Hex(next), expiresAt: addTime(now, 30, "d"), deviceInfo: row.deviceInfo })`;
      `markRotated(row.id, newId)` (0 rows → throw, rollback, 500); `accessToken = signer.signUserToken(user)`
      (signed **before** commit so a signing failure cannot strand a rotated family); commit.
7. **rotated** → 200 + `Set-Cookie` with `next`.

`pending` and `rejected` users refresh normally; the new token carries the live `role`, `status`, and `ev`.
Query count on success: 1 lookup + 3 statements in the tx (lock, user read, insert) + 1 update = 5, plus 1 Redis call.

### 4.5 Cookie helpers (`src/lib/http/cookies.ts`)
- `readCookie(req, name): string | undefined` — parses the `Cookie` header (split on `;`, first `=`, trim; no
  decoding beyond `decodeURIComponent` guarded by try/catch; duplicate names → first wins).
- `setRefreshCookie(res, token)` → `vcare_rt=<token>; HttpOnly; Secure; SameSite=Strict; Path=/api/auth; Max-Age=2592000`
  (`REFRESH_TOKEN_TTL_SECONDS` constant). `Secure` is always set (browsers treat `localhost` as secure; CURL ignores it).
- `clearRefreshCookie(res)` → `vcare_rt=; HttpOnly; Secure; SameSite=Strict; Path=/api/auth; Max-Age=0`.
- Refresh tokens and cookie headers are never logged; the request logger never logs headers (foundation).

### 5.2 `src/lib/password/`
- `semaphore.ts`: `class Semaphore(max, queueMax)` with `run<T>(fn): Promise<T>`; when `max` are running and
  `queueMax` are waiting it rejects immediately with `HashQueueFull` (never waits unbounded). FIFO queue.
- `password-hasher.ts`: `class PasswordHasher(semaphore, logger)`:
  - `hash(plain)` → `argon2.hash(plain, { type: argon2id, memoryCost: 19456, timeCost: 2, parallelism: 1 })`.
  - `verify(stored, plain): Promise<{ ok: boolean; needsRehash: boolean }>` — `$argon2id$` → `argon2.verify`,
    `needsRehash = argon2.needsRehash(stored, params)`; `$2a$`/`$2b$`/`$2y$` → `bcrypt.compare`, `needsRehash = ok`;
    any other prefix → `{ ok: false, needsRehash: false }` plus `warn password_hash_unrecognized { }`. Library errors
    on a malformed hash are treated as `ok: false`.

  - All three run inside `semaphore.run`. `HashQueueFull` → `RateLimited` with `Retry-After: 1` (the error handler
    sets the header when `AppError.retryAfterSeconds` is present — small foundation extension; `rateLimit` keeps
    setting it itself). Metrics: `hash_rejected` (count, on each rejection), `hash_queue_depth` (gauge, at most once
    per 10 s while the queue is non-empty).
  - Never compares with `===`; never logs inputs.

  (MIT), lower-cased, filtered to 10..128 characters, de-duplicated, sorted; the generated file records source URL,
  commit SHA, and licence in its header comment. Size is expected in the low thousands of entries (< 100 KB).
  Loaded once; lookups are O(1).
- `is-acceptable-password.ts`: the `IsAcceptablePassword` class-validator decorator.
- The ops runbook hash: `scripts/unusable-password-hash.ts` prints only `argon2id(randomBytes(64))` (ADR 0010).

### 5.4 `src/lib/outbox/`
- `types.ts`: `OutboxJobType = "send_registration_code" | "send_account_exists_notice" | "send_password_reset"`,
  `OutboxJob { id, type, aggregateId, attempts, requestId }`, `JobHandler = (job, signal) => Promise<JobResult>`,
  `JobResult = "sent" | "skipped"`, `OutboxDeliveryError { retryable: boolean; errorClass: string }`.
- `outbox.repo.ts` (functions, `conn`):
  - `enqueue(conn, type, aggregateId, requestId)` → `INSERT INTO outbox_jobs (type, aggregate_id, status, attempts, run_after, request_id) VALUES ($1, $2, 'pending', 0, now(), $3)`.
    Always called with the caller's transaction. `requestId` = `getRequestContext().requestId`.
  - `claim(limit, leaseSeconds)` →
    `UPDATE outbox_jobs SET status = 'processing', attempts = attempts + 1, locked_until = now() + make_interval(secs => $2), updated_at = now() WHERE id IN (SELECT id FROM outbox_jobs WHERE status = 'pending' AND run_after <= now() ORDER BY run_after LIMIT $1 FOR UPDATE SKIP LOCKED) RETURNING id, type, aggregate_id, attempts, request_id`.
  - `reclaimExpiredLeases(limit, maxAttempts)` → jobs `status = 'processing' AND locked_until < now()` (same
    `SKIP LOCKED` sub-select) become `pending` with `run_after = now()`, or `dead` with `completed_at = now()` when
    `attempts >= maxAttempts`; `last_error = 'LeaseExpired'`, `locked_until = NULL`. Returns the count.
  - `markDone(id)` → `status = 'done', completed_at = now(), locked_until = NULL, last_error = NULL, updated_at = now() WHERE id = $1 AND status = 'processing'`.
  - `markRetry(id, delaySeconds, errorClass)` → `status = 'pending', run_after = now() + make_interval(secs => $2), locked_until = NULL, last_error = $3`.
  - `markDead(id, errorClass)` → `status = 'dead', completed_at = now(), locked_until = NULL, last_error = $2`.
  - `oldestDuePendingAgeSeconds()` → `SELECT EXTRACT(EPOCH FROM now() - min(run_after)) FROM outbox_jobs WHERE status = 'pending' AND run_after <= now()` (0 when none).
  - `deleteFinishedBatch(status: "done" | "dead", olderThanDays, limit, trx)`.
- `backoff.ts`: `retryDelaySeconds(attempts) = min(30 × 2^(attempts − 1), 3600)` (30 s, 1 m, 2 m, … capped at 1 h).
- `outbox-processor.ts`: `class OutboxProcessor({ db, logger, handlers: ReadonlyMap<OutboxJobType, JobHandler>, batchSize, maxAttempts, concurrency: 4, leaseSeconds: 120 })`
  with `tick(signal)`:
  1. `reclaimExpiredLeases(batchSize, maxAttempts)`; count > 0 → `warn outbox_lease_reclaimed { count }`.
  2. `jobs = claim(batchSize, 120)`; process with at most 4 concurrent handlers; stop starting new jobs once
     `signal.aborted` (their leases expire and are reclaimed).
  3. Per job, inside `requestContext.run({ requestId: job.requestId })` so log lines carry the originating request id:
     handler → `"sent"`: `markDone`, `info outbox_job_sent { jobId, type, attempts }`; `"skipped"`: `markDone`,
     `info outbox_job_skipped { jobId, type }`; `OutboxDeliveryError` retryable and `attempts < maxAttempts` →
     `markRetry(retryDelaySeconds(attempts))`, `warn outbox_job_retry { jobId, type, attempts, errorClass }`;
     non-retryable or attempts exhausted → `markDead`, `error outbox_job_dead { jobId, type, errorClass }`, metric
     `outbox_dead_jobs` (dimension `type`); any other thrown error → treated as retryable with `errorClass = err.name`.
  4. At most once per 60 s: metric `outbox_oldest_pending_age_s` (no dimension).
- Lease 120 s > worst case of a job (5 s provider timeout plus two short statements) × the queue depth behind it at
  concurrency 4 with batch 20.

    `markSent(id, hmacSha256Hex(OTP_PEPPER, code))` (overwrites any code from an earlier delivery attempt;
    `attempts` unchanged); commit; then `emailPort.send(...)`. The plaintext code exists only in memory and the email.
  - Hash first, send second: a crash after send and before `markDone` re-sends a **new** secret that supersedes the
    first (at-least-once, ADR 0007).

### 5.6 Purges (`PurgeService`, worker only)
Run by a second worker loop every **10 minutes** (`PURGE_INTERVAL_MS` constant). For each step, repeat
`withAdvisoryXactLock(db, key, trx => deleteBatch(5000, trx))` until a batch deletes fewer than 5000 rows, the lock is
not acquired, 20 batches ran, or the stop signal fired. Each batch is its own short transaction (well under the 2 s
statement timeout). Lock keys are fixed `bigint` constants per step (`0x7661_0001n` … `0x7661_0005n`).
| Step | Delete condition | Index |
|---|---|---|
| `refresh_tokens` | `expires_at < now() - interval '30 days'` | `idx_refresh_tokens_expires_at` |
| `password_resets` | `created_at < now() - interval '30 days'` | `idx_password_resets_created_at` |
| `registration_challenges` | `created_at < now() - interval '24 hours'` | `idx_registration_challenges_created_at` |
| `outbox_jobs` done | `status = 'done' AND completed_at < now() - interval '7 days'` | `idx_outbox_jobs_completed_at` |
| `outbox_jobs` dead | `status = 'dead' AND completed_at < now() - interval '30 days'` | `idx_outbox_jobs_completed_at` |
Each step logs `purge_completed { table, deleted, batches }` at `info` when `deleted > 0`. `users` and (later)
`user_status_changes` are never purged.

## 7. Business rules
| # | Rule | Enforced by |
|---|---|---|
| BR-1 | `register/start` returns `202` with no body for known, unknown, and malformed-but-valid emails alike; known live email → `send_account_exists_notice` job only (no challenge); unknown → earlier open challenges invalidated, new challenge + `send_registration_code` job, in one tx | service (`RegistrationService.start`), tx |
| BR-2 | A registration code is 6 CSPRNG digits generated by the worker at send time, stored only as `HMAC-SHA256(OTP_PEPPER, code)` hex, valid 10 minutes from send | worker (`AuthMailService`), `chk_registration_challenges_code_sent`, `chk_registration_challenges_code_hash_hex` |
| BR-3 | `register/complete` uses only the latest open challenge for the email, compares in constant time, counts every checked attempt, invalidates the challenge on the 5th failure, and never accepts a consumed, invalidated, unsent, or expired challenge; every failure is `400 ValidationFailed field=code` | service + `FOR UPDATE` tx, `chk_registration_challenges_attempts` (0..5) |
| BR-4 | A successful `register/complete` consumes the challenge and creates the user with `email_verified_at = now()` in the same tx; `role ∈ {patient, doctor}`; patient → `active`, doctor → `pending`; never admin | DTO `@IsIn`, service, tx, `chk_users_role`/`chk_users_status` |
| BR-5 | At most one live account per email (case-insensitive); a lost race → `409 Conflict`, challenge not consumed | `uq_users_email` (CITEXT, partial), service maps `23505` |
| BR-6 | `register/complete` requires `Idempotency-Key`; same key + body replays `201`; different body → `422`; with Redis down, duplicates are stopped by BR-3/BR-5 (`400`/`409`) | `idempotency({ required: true })`, DB constraints |
| BR-7 | Login: unknown email and wrong password both return `401 InvalidCredentials` after one argon2 verify (dummy for unknown) | service, `PasswordHasher.verifyDummy` |
| BR-8 | Login and refresh are allowed for `pending`, `active`, `rejected`; `suspended` → `403 AccountSuspended` (login: only after a correct password) | service |
| BR-9 | A successful login creates a new refresh family (random UUID), stores only sha256 of a 256-bit token, expires in 30 days, and returns the token only in the `vcare_rt` cookie | service, `chk_refresh_tokens_token_hash_hex`, response DTO |
| BR-10 | A legacy bcrypt hash or an argon2id hash with weaker parameters is rehashed with argon2id on successful login; a full hash queue skips the rehash without failing login | `PasswordHasher`, service |
| BR-11 | Refresh rotates in one tx: the presented token is locked, marked `rotated` with `replaced_by_id`, and a new token of the same family is inserted; a token has at most one successor | service tx, `uq_refresh_tokens_replaced_by_id`, `chk_refresh_tokens_replaced_by_rotated` |
| BR-12 | Re-presenting a rotated token revokes every live token of its family (`reuse_detected`) and returns `401 RefreshTokenReused` with a clearing cookie — unless BR-13 applies | service |
| BR-13 | Grace: rotated < `REFRESH_REUSE_GRACE_SECONDS` ago and successor live → `401 RefreshTokenInvalid`, no revocation, no `Set-Cookie` | service |
| BR-14 | Refresh re-reads the user; `suspended` → revoke the family (`status_changed`), `403 AccountSuspended`, clearing cookie; soft-deleted → `401 RefreshTokenInvalid` | service tx |
| BR-15 | Unknown, malformed, expired, or otherwise revoked refresh tokens → `401 RefreshTokenInvalid` with a clearing cookie | service, controller |
| BR-16 | Refresh is limited to 30/min per family and fails open when Redis is down | `consumeRateLimit` (`fail-open`) |
| BR-17 | Logout revokes every live token of the presented token's family (`logout`), clears the cookie, and always returns `204` | service, controller |
| BR-18 | Forgot-password always returns `204`; for a live account (any status) it invalidates earlier open reset rows and enqueues a new one in one tx | service tx |
| BR-19 | A reset code is 6 CSPRNG digits generated by the worker at send time, stored only as `HMAC-SHA256(OTP_PEPPER, code)` hex, valid 30 minutes from send, single use, max 5 checked attempts (the 5th failure invalidates the row); a newer forgot-password request invalidates earlier open rows | worker (`AuthMailService`), service + `FOR UPDATE` tx, `chk_password_resets_code_sent`, `chk_password_resets_attempts` (0..5), `chk_password_resets_code_hash_hex`, `markUsed` guard |
| BR-20 | Reset uses only the latest open row of the user resolved from `email` among live rows, compares in constant time, then sets the new argon2id hash, marks the row used, invalidates any other open row, and revokes **all** families (`password_reset`) — all in one tx | service tx |
| BR-20a | Every reset failure — unknown email, wrong code, never-sent, expired, used/superseded, or exhausted row — returns the **identical** `400 ValidationFailed` with `details[0].field = "code"`, after the same work (argon2 hash of `newPassword` always runs first; a dummy HMAC compare runs when there is no candidate row), so reset cannot be used to enumerate accounts | service (single failure path, no early return) |
| BR-21 | Change-password requires the current password (`401 InvalidCredentials` otherwise) and revokes all families except the one of the `vcare_rt` cookie sent with the request when that token belongs to the caller; no such cookie → all families | service tx |
| BR-22 | New passwords are 10..128 characters and not on the denylist | DTO (`Length`, `IsAcceptablePassword`) |
| BR-23 | `PATCH /me` changes only `fullName`, `phone`, `avatarUrl`, `timezone`, `locale`; any other property → `400`; empty body → `400`; `timezone` is a valid IANA zone and `locale` a BCP-47 tag, stored canonical | DTO (`forbidNonWhitelisted`, custom validators), `chk_users_phone_e164`, `chk_users_full_name_not_blank` |
| BR-24 | Self routes serve any non-suspended live account (`pending`, `active`, `rejected`); a suspended row → `403 AccountSuspended` even with a still-valid access token; a soft-deleted or unknown subject → `401 Unauthorized` | `authorize(selfPolicy)` (claim) + service row check |
| BR-25 | Access tokens are EdDSA, `kid`-tagged, 900 s, with exactly the contract claims; expired → `401 TokenExpired`, any other defect (bad signature, unknown `kid`, wrong `iss`/`aud`/`typ`, malformed claims) → `401 Unauthorized` | `lib/auth/jwt.ts`, `user-guard` |
| BR-26 | JWKS publishes the public half of every configured key and never private material | `lib/auth/jwks.ts` |
| BR-27 | Every route has `authorize(policy)`; the app refuses to start otherwise | `authorize`, `assertRoutesAuthorized` |
| BR-28 | Outbox jobs are inserted in the same tx as their business row and hold only `type`, `aggregate_id`, `request_id` — no PII, no secrets | `lib/outbox/outbox.repo.ts` (column set), tests |
| BR-29 | A job is claimed by one worker at a time (`SKIP LOCKED` + lease); expired leases are reclaimed; retries back off; after `OUTBOX_MAX_ATTEMPTS` the job is `dead`; `last_error` holds an error class only | `OutboxProcessor`, `chk_outbox_jobs_lease`, `chk_outbox_jobs_completed` |
| BR-30 | Jobs whose aggregate is gone, consumed, used, or invalidated are completed as `skipped` without sending | `AuthMailService` |
| BR-31 | Purges delete only rows past retention (5.6), in batches of 5 000 under an advisory lock; `users` rows are never deleted | `PurgeService`, `withAdvisoryXactLock` |
| BR-32 | Every `/api/auth/*` response carries `Cache-Control: no-store`; JWKS carries `public, max-age=300` | router-level `noStore()`, JWKS controller |
| BR-33 | Credential-route limiters run before validation and hashing and fall back in-process when Redis is down; argon2 runs behind the semaphore and a full queue returns `429 RateLimited` | route wiring, `rateLimit`, `Semaphore` |
| BR-34 | Change-password is limited to 5 per 15 minutes per authenticated user id (fallback degrade) and returns `429 RateLimited` with `Retry-After` beyond that, so a stolen access token cannot be used to brute-force the current password | `change-password-user` limiter after `authorize` |
| BR-35 | Login neither honours nor stores an `Idempotency-Key`: no access token is ever written to Redis, and a repeated login creates a new refresh family instead of replaying a token without its cookie | route wiring (middleware not mounted) |

## 9. Security & privacy

### 9.1 RBAC summary
| Route | Guard | Roles | Ownership | Account state |
|---|---|---|---|---|
| `POST /api/auth/register/start`, `/register/complete`, `/login`, `/forgot-password`, `/reset-password`, `GET /.well-known/jwks.json` | none | public | none | login: `pending`/`active`/`rejected` |
| `POST /api/auth/refresh`, `/logout` | refresh cookie | patient, doctor, admin (the cookie owner) | the presented token's family | refresh: not `suspended` |
| `POST /api/auth/change-password`, `GET /api/auth/me`, `PATCH /api/auth/me` | user token | patient, doctor, admin | self (acts on `req.auth.userId` only) | `pending`, `active`, `rejected` |
Discrepancy flagged: CLAUDE.md → Authorization's route table says refresh requires "not suspended/rejected"; ADR 0004
and the contract allow `rejected`. This spec follows the contract (12.2).

### 9.2 Secrets and data at rest
- Passwords: argon2id (`memoryCost=19456`, `timeCost=2`, `parallelism=1`); bcrypt only verified.
- Refresh tokens: sha256 hex of 256-bit random values. Registration **and** password-reset codes: 6 digits stored as
  `HMAC-SHA256(OTP_PEPPER, code)` hex — a keyed hash, so a database dump alone cannot brute-force the 10^6 space.
- Plaintext codes exist only in worker memory, the email, and (development/test only) the capture file.
- Signing keys only from `JWT_PRIVATE_KEYS`; never in the repo, logs, DB, or JWKS (`d` never published).
- **No access token is ever stored in Redis** (D-1): login mounts no idempotency middleware, so the foundation's
  24 h response-replay record — which holds a status and body but no headers — never captures a bearer token.
- **Accepted trade-off (D-1, `register/complete`)**: the contract requires `Idempotency-Key` there, so the standard
  middleware stays and its replay record holds the created `User` body — **email, phone, and fullName in Redis for
  24 h**. Accepted because (a) Redis is treated as non-durable cache state, not a system of record
  (`data-model.md` → "Redis keys (non-durable)"; ADR 0008 makes it Tier 2), (b) the record expires after 24 h,
  (c) it is keyed to `(route, ip principal, key)` plus a body hash, so only the same caller with the same body can
  replay it, and (d) Redis is private, with TLS in non-local environments. The alternative — storing status
  plus user id and re-reading the user on replay — is a foundation change with its own consistency questions and is
  not worth it for a 24 h window; revisit if Redis ever becomes durable or shared.

### 9.3 Log events (no PII, no secrets; ids only)

### 9.4 Never logged, and redaction additions
Never passed to the logger: passwords, hashes, access and refresh tokens, registration and password-reset codes,

### 9.5 Rate limits and abuse controls
| Limiter | Route | Subject | Limit | Window | Degrade |
|---|---|---|---|---|---|
| `register-start-email` | register/start | sha256(lower(email)) | 3 | 1 h | fallback |
| `register-start-ip` | register/start | IP | 5 | 1 h | fallback |
| `register-complete-ip` | register/complete | IP | 10 | 1 h | fallback |
| `login-ip-email` | login | IP + sha256(lower(email)) | 5 | 1 min | fallback |
| `login-ip` | login | IP | 20 | 1 min | fallback |
| `forgot-email` | forgot-password | sha256(lower(email)) | 3 | 1 h | fallback |
| `reset-email` **(new, D-3)** | reset-password | sha256(lower(email)) | 5 | 1 h | fallback |
| `reset-ip` | reset-password | IP | 10 | 1 h | fallback |
| `refresh-family` | refresh | `family_id` | 30 | 1 min | fail-open |
| `change-password-user` **(new, D-2)** | change-password | authenticated user id | 5 | 15 min | fallback |
Plus: 5 attempts per registration challenge, 5 attempts per reset row; hash semaphore (`HASH_CONCURRENCY`,
`HASH_QUEUE_MAX`). Both new limiters go into CLAUDE.md → Security rules and `infrastructure.md` (12.2).
- **Why `reset-email` = 5/h.** The 5-attempt cap protects one reset row, but an attacker could call forgot-password
  (3/h per email) to mint fresh rows and keep guessing, and `reset-ip` alone is evadable from many IPs. A per-email
  cap of 5 guesses per hour bounds the attack to the same 5 tries the row itself allows, and is consistent with it
  (one honest user needs at most 1–2). Evaluated **before** `reset-ip` so a distributed attack on one account is
  stopped first.
- **Why `change-password-user` = 5/15 min.** The route verifies the current password, so a stolen access token is a
  brute-force surface; 5 tries per 15 min is generous for a human (typo, retry) and useless for guessing, and the
  subject is the user id rather than the IP so the limit follows the victim, not the network path.

Residual accepted risks: forgot-password for a known email performs writes while an unknown email does not, so
response time differs by a few milliseconds (email delivery itself is asynchronous and uniform); a thief replaying
within the 10 s grace window gets no token and no revocation (ADR 0005).

### 9.6 One-time code entropy (registration and reset)
A 6-digit code carries ~20 bits of entropy, versus 256 bits for the base64url token the v1.0.0 draft emailed for
reset. The blind-guess probability per attempt is 10^-6, and the guardrails below bound the total exposure:

| Control | Registration challenge | Password reset |
|---|---|---|
| Attempt cap per row | 5, 5th failure invalidates the row | 5, 5th failure invalidates the row (BR-19) |
| Validity from send | 10 min | 30 min |
| Single use | `consumed_at` | `used_at` |
| Superseded by a newer request | yes (`invalidated_at`) | yes (`invalidated_at`) |
| Storage | `HMAC-SHA256(OTP_PEPPER, code)` — keyed, so a DB dump cannot be brute-forced offline without the pepper | same |
| Per-email request limiter | 3/h (`register-start-email`) | 3/h (`forgot-email`) |
| Guess limiter on the submit route | 10/h per IP (`register-complete-ip`) | 5/h per email (`reset-email`) + 10/h per IP (`reset-ip`) |
| Constant-time compare | `timingSafeEqualHex` | `timingSafeEqualHex` |

Worst case for reset: 5 guesses per hour per email, against a 10^6 space and a 30-minute window → ≈ 5×10^-6 chance
per hour of attack, and a successful guess still only reaches a password change that revokes every session and is
logged and alertable. The code never travels in a URL, which removes the link-leak class of attack that the
256-bit token had (proxy logs, `Referer`, browser history, shared links, and prefetching by mail clients) and makes
the flow identical to registration for both users and code. This mirrors ADR 0006's reasoning for registration; see
the ADR recommendation in 14.1 (D-3).

### 9.7 Headers and transport
`Cache-Control: no-store` on every `/api/auth/*` response; cookie attributes per 4.5; access token only in the body
and `Authorization`; `helmet` defaults (foundation). No files are uploaded or downloaded by this module.

| Path | Work | Queries | Budget (p95) |
|---|---|---|---|
| `POST /login` | 2 Redis limiter calls, 1 read (`uq_users_email`), 1 argon2 verify, 1 tx (insert token [+ rehash update]), 1 EdDSA sign | 2–3 + BEGIN/COMMIT | < 250 ms |

| `POST /register/complete` | 1 Redis + idempotency, argon2 hash, 1 tx (lock, 1–2 updates, insert user, idempotency store) | 3–4 | < 200 ms + hash |

### 14.1 Decisions recorded (v1.1.0)
**D-1 — Login accepts no `Idempotency-Key`; `register/complete` keeps the standard middleware.**
The foundation middleware stores the response **body** in Redis for 24 h and replays status + body **without
headers**. On login that would (a) persist a live access token in Redis in plaintext (CLAUDE.md → Database rules:
secrets are never stored in plaintext) and (b) replay a token with no refresh cookie, leaving the client with an
access token it cannot renew. Decision: drop idempotency from login entirely — the middleware is not mounted, the
header is ignored, and the contract loses `IdempotencyKeyOptional`, `IdempotencyConflict`, and the `'422'` response
(C-1). Login is naturally safe to retry: a retry simply creates another refresh family, and abuse is bounded by
`login-ip-email` 5/min and `login-ip` 20/min. Rejected: a body-less idempotency variant (a lib change whose replay
would have nothing to return, so it would re-execute anyway) and keeping the contract as is (tokens in Redis).
For `register/complete` the contract **requires** the header, so the standard middleware stays and its 24 h replay
record holds the created `User` body — email, phone, fullName in Redis for 24 h. Accepted with the mitigations and
the revisit trigger written into 9.2.

**D-2 — Change-password gets a per-user limiter and a `429`.** The route verifies the current password (a
brute-force surface for a stolen access token) and hashes a new one (the bounded semaphore must be able to answer
`429` rather than wait). Decision: limiter `change-password-user` — subject the authenticated user id, 5 per
15 minutes, degrade `fallback` — mounted after `authorize(selfPolicy)`; contract gains `RateLimited` and a `'429'`
response (C-2). Numbers justified in 9.5. Rejected: `429` only for the hash queue (leaves the password-guessing
surface open) and no `429` at all (would mean an unbounded wait, forbidden by CLAUDE.md → Security rules).

**D-3 — Password reset is a typed 6-digit code, mirroring the registration challenge.** This supersedes the
`OneTimeToken` link design of v1.0.0 everywhere in this spec. `POST /api/auth/reset-password` takes
`{ email, code, newPassword }`; the worker generates 6 CSPRNG digits at send time, stores
`HMAC-SHA256(OTP_PEPPER, code)` in `password_resets.code_hash`, 30 minutes from send, single use, **max 5 attempts**
with the 5th failure invalidating the row, and a newer forgot-password invalidating earlier open rows (2.3, 3.8,
BR-19/BR-20/BR-20a). The email carries the code and the bare `<APP_BASE_URL>/reset-password` path — **no secret in
any URL**. Rationale: one mechanism and one mental model for both one-time secrets (same table shape, same
`recordFailedAttempt`/`markSent` repo functions, same tests), no link-leak class of attack (proxy logs, `Referer`,
browser history, shared or prefetched links), no web-client fragment contract, and it works when the mail client
strips links. Entropy trade-off — 20 bits instead of 256 — is analysed in 9.6 and bounded by the 5-attempt cap, the
30-minute TTL, single use, the keyed hash, `reset-email` 5/h, `reset-ip` 10/h and `forgot-email` 3/h.
**ADR recommendation:** this decision warrants its own ADR (suggested **ADR 0017 — password reset by one-time code**,
superseding nothing but extending ADR 0006's reasoning to reset) because it changes a security mechanism, a table,
and the contract. The user decides; the developer's ADR 0016 remains the runtime-dependency ADR (12.1).
