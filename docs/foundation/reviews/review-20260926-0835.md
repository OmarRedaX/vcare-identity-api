## High
- [ ] OPEN — [High] Idempotency stores a handler-thrown `429` as `completed` for 24 h, so a correct same-key retry replays `429` forever (without `Retry-After`) · `src/lib/idempotency/idempotency.ts:180`
  - Scenario: under a credential-stuffing burst (deployment.md bottleneck 2) the argon2 queue fills; `POST /api/auth/register/complete` with key K passes the limiter and the claim, then `hasher.hash` rejects with `HashQueueFull` (`src/lib/password/semaphore.ts:7`, `429`, `Retry-After: 1`). `status < 500` → `store(...completed, status 429...)` with `PX 86400000`. The client obeys `Retry-After` and retries with the same K and body → row 7 replays `429` (headers are not stored, so no `Retry-After`), the handler never runs again. The registration code expires in 10 min, so the user must restart registration. Same for `reset-password` / `change-password` / `register/start` / `forgot-password` when a key is sent.
  - Rule: CLAUDE.md → Security rules ("a full queue returns `429 RateLimited`" — a transient refusal) and API conventions → Idempotency (replay the *original* outcome, not a throttle); spec F5. Root cause is spec §4.12 row 5a ("status < 500 → store").
  - Fix: in `beginHandler`'s completion callback treat `status === 429` like `>= 500` (`DEL key`). **Spec first:** amend §4.12 rows 5a/5b ("429 and ≥ 500 → DEL") and the unit-test list. **Care parity:** same change in care's idempotency middleware and spec.
  - Test gap: unit "should delete the record when the handler finishes with 429"; integration: a test route that throws `RateLimited.withRetryAfter(1)` once then succeeds → second same-key call returns 201.

## Medium
- [ ] OPEN — [Medium] Graceful shutdown never drains a keep-alive connection that had a request in flight at SIGTERM → `shutdown_timeout`, exit 1 · `src/server.ts:34-41` (used at `:85-106`)
  - Scenario: reproduced on Node 24.11.0 with `keepAliveTimeout = 65000`: a keep-alive client has a 500 ms request in flight; `server.close()` + one `closeIdleConnections()` run at t=117 ms; the response goes out at t=519 ms still carrying `Connection: keep-alive`; the socket is now idle but nobody closes it, so the `close` callback does not fire within 12 s. With `SHUTDOWN_TIMEOUT_MS=10000` this logs `error shutdown_timeout {unfinishedRequests: 0}`, calls `closeAllConnections()`, and exits 1 — every stop that coincides with LB keep-alive traffic produces a false error and a 10 s stall.
  - Rule: spec F10 / §4.17 shutdown step 3 (drain, then exit 0); CLAUDE.md → Folder structure (`server.ts` graceful shutdown).
  - Fix: once shutting down, close sockets as their last request ends — e.g. in `inflightTracker`'s end hook (or `server.on("request")`) set `res.setHeader("Connection", "close")` while `lifecycle.isShuttingDown()`, and/or call `closeIdleConnections()` on both servers from `requestEnded()` during shutdown. **Care parity.**
  - Test gap: `process.test.ts` (or a unit test on a real `http.Server`): keep-alive agent + slow request + SIGTERM mid-request → exit 0 well before the deadline.

- [ ] OPEN — [Medium] Idempotency claim that times out client-side (or is resent by ioredis after a reconnect) lands later and leaves an orphan `in_flight` record → same-key retries get `409` for 60 s · `src/lib/idempotency/idempotency.ts:169-176`, `:234-236`; `src/lib/redis/redis.ts:12-19`
  - Scenario A: Redis answers `SET … NX PX 60000` in 150 ms. `withTimeout(…, 100)` rejects → `run().catch` → `skip("redis_error")` → the handler runs untracked and returns 201. The un-cancellable `SET NX` then succeeds, writing `{state:"in_flight"}` that nobody stores over or deletes. The client's same-key retry within 60 s gets `409 Conflict` + `Retry-After: 1` (row 8) instead of a replay; after 60 s the handler re-executes (`register/complete` → `400 field: code` / `409` instead of the original 201). Scenario B: a Redis connection drop while the `SET NX` is on the wire — ioredis keeps `prevCommandQueue` and, with the default `autoResendUnfulfilledCommands: true` and `maxRetriesPerRequest: 1` (first reconnect does not flush, `event_handler.js` closeHandler/readyHandler), resends it after reconnect, long after the request skipped. The same resend double-counts in-flight rate-limit script calls (one extra hit per affected request).
  - Rule: spec F6 ("a Redis outage never fails a request") and §4.12 row 10 (skip means the middleware has no effect).
  - Fix: (1) `createRedis`: `autoResendUnfulfilledCommands: false`; (2) in `claim()`, if the timed-out `SET` later resolves `"OK"`, issue a compare-and-delete (store a random nonce in the record; Lua `if GET == record then DEL`). Mention the compensation in spec §4.12 row 10. **Care parity** (both the middleware and `redis.ts` options).
  - Test gap: unit — mocked `set` resolving `"OK"` after 150 ms → the key is deleted and the next same-key call runs the handler; unit on `createRedis` options.

- [ ] OPEN — [Medium] `TRUST_PROXY_HOPS` silently defaults to `0` in production and one value is applied to two listeners with different hop counts · `src/lib/config/env.schema.ts:98`, `src/app.ts:22`, `src/internal-app.ts:19`, `src/lib/http/client-ip.ts:7`
  - Scenario: a production task started without the variable (deployment.md:37 only *documents* it) sees every client as the ALB node address. All per-IP limiters then act platform-wide: `login-ip` 20/min, `register/start` 5/h per IP, `register/complete` 10/h per IP, `reset` 10/h per IP — a handful of users lock out everyone, and `ip:` idempotency principals collide across users. Nothing fails loudly. Conversely the public edge is CloudFront + ALB (2 hops) while the internal listener sits behind one internal LB, so a single value is necessarily wrong for one listener (too high → the caller's own `X-Forwarded-For` is trusted). The internal side is latent today (no IP-keyed decision on `/internal/*` yet).
  - Rule: CLAUDE.md → Security rules (rate limits per IP; env validated, process refuses to start on invalid env); spec §4.2, §11.4.
  - Fix: `superRefine` — in `production`, reject an unset `TRUST_PROXY_HOPS` (require it explicitly, ≥ 1); add `INTERNAL_TRUST_PROXY_HOPS` for `createInternalApp`. **Spec first:** §4.2 env table + infrastructure.md §1.
  - Test gap: `load-env` rejects production without the variable; integration: `X-Forwarded-For` ignored at 0 and honoured at N on each listener.

- [ ] OPEN — [Medium, latent] Unknown errors are logged with their raw `message` and `stack`; Postgres class-22 messages carry the offending input value · `src/lib/error/errorHandler.ts:57`, `:64`, `:98`; `src/lib/logger/redact.ts:57-66`; also `src/lib/worker/run-loop.ts:33`, `src/server.ts:144`, `:148`, `src/worker.ts:124`, `:128`, `src/migrate.ts:75`

Any `Error` whose message embeds a secret is logged verbatim too — `tests/helpers/test-routers.ts:47-49` throws `"db password=synthetic-value"` and `tests/integration/logging.test.ts` never asserts its absence. Knex itself does **not** splice bound values into the message for pg (see evidence note below), and pg's `detail` (e.g. `Key (email)=(…)` on 23505) is not serialized. Latent: every current route validates input with DTOs before it reaches a typed column, so no present path has been shown to leak.
  - Rule: CLAUDE.md → Privacy and logging ("never log … email addresses …"); spec F8. Tension with "Errors log the stack server-side only" and spec §4.4 row 8 (`{ err }` with name, message, stack).
  - Fix: a `serializeError` policy for non-`AppError` errors: `{ name, code, constraint?, table?, column?, routine? }`, message replaced by `pg_error:<SQLSTATE>` for driver errors (generic `error:<name>` otherwise), stack frames without the header line; optionally `compileSqlOnError: false` to drop the SQL prefix. **Spec first:** §4.4 row 8 and §4.6 (and a human CLAUDE.md wording on what "log the stack" includes). **Care parity** (same `redact.ts` mechanics per spec §12).

  - Evidence note (knex interpolation, settles the IS2/IC2 conflict): `node_modules/knex/lib/execution/internal/query-executioner.js` (knex **3.3.0**, byte-identical in care) calls `formatQuery(queryObject.sql, queryObject.bindings, …)` unless `compileSqlOnError === false`, but `enrichQueryObject` already ran pg's `positionBindings`, so the SQL holds `$1…$n` and `formatQuery`'s `?` scan finds nothing — values are **not** interpolated (reproduced: statement-timeout insert logs `values ($1, $2)`). Exception: a SQL text containing an escaped literal `\?` (jsonb `?` operators) becomes a bare `?` after positioning and **does** receive a bound value (reproduced: `'{"k":1}'::jsonb 'person@example.test' 'k'`). No `\?` exists in identity `src/` today.

- [ ] OPEN — [Medium] Readiness `SELECT 1` competes for the shared 10-connection request pool, so pool saturation reads as "Postgres down" · `src/app/health/service/health.service.ts:56-66`, `src/app/health/repository/health.repo.ts`, `src/bootstrap.ts` (Db token), `src/lib/knex/knexfile.ts:40-50`
  - Scenario: a burst or lock contention (e.g. `refresh_tokens` rotation plus a purge batch) keeps all `DATABASE_POOL_MAX=10` connections busy for up to the 2 s statement timeout; the probe's acquire waits past its 500 ms race → `database: down` → `503` on every task at once while Postgres is healthy. The LB marks targets unhealthy and the orchestrator replaces tasks during exactly the overload that needs capacity; runbook `HealthCheckFailing` then points on-call at DB connectivity.
  - Rule: spec F3 ("503 iff Postgres is down or shutting down"); ADR 0014 (readiness fatal on Postgres only).
  - Fix: probe through a dedicated single-connection client (`pg.Client`/1-connection pool with `connectionTimeoutMillis`) so it measures Postgres reachability, not pool headroom; emit pool-saturation as its own signal. **Spec first:** §3.2 / §4.16 (and an ADR 0014 note).
  - Test gap: integration — hold all pool connections with `pg_sleep` and assert readiness stays `200`.

- [ ] OPEN — [Medium] No client-side Postgres timeouts or TCP keep-alive: a failover that blackholes connections hangs queries until the kernel gives up · `src/lib/knex/knexfile.ts:33-53`; `src/server.ts:108`; `src/worker.ts` (`db.destroy()`)
  - Scenario: pg 8.23 defaults `query_timeout: false`, `connect_timeout: 0`, JS `keepAlive: false`; tarn `createTimeoutMillis` defaults to 30 s. `statement_timeout` is server-side and cannot fire when the old primary vanishes without RST (AZ loss). In-flight queries hang on dead sockets (Linux retransmission ≈ 15 min), the pool stays full, every request fails after the 1 s acquire, readiness is 503, and SIGTERM's `db.destroy()` waits on the hung connections until SIGKILL. deployment.md bottleneck 4 claims "~60 s … reconnect", which the code does not deliver.
  - Rule: spec F12 (every pooled connection has bounded statements); deployment.md bottleneck 4; CLAUDE.md → Mission (Tier 1).
  - Fix: `connection: { …, query_timeout: 3000, connectionTimeoutMillis: 2000, keepAlive: true, keepAliveInitialDelayMillis: 10000 }`, `pool.createTimeoutMillis: 2000`; race `db.destroy()`/`redis.quit()` against the remaining shutdown budget. **Spec first:** §4.10.
  - Test gap: unit on `buildKnexConfig` asserting the options; unit on shutdown with a never-resolving `db.destroy()` → still resolves within the deadline.
